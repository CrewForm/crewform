# Upgrading to CrewForm 1.11.0

This minor release adds inspectable pipeline handoffs, committed checkpoints,
human continuation decisions and sequential personal-device pipelines. CrewForm
software is MIT and free to self-host; payments apply only to Cloud resources.
Existing published releases and npm versions retain their original licences.

## Coordinated upgrade

1. Follow the [release checklist](README.md) and capture the actual schema,
   migration history and application/runner/Edge versions. Export the database
   and private Storage objects, verify an offline restore, and preserve the
   existing encryption key separately. Do not replay historical migration IDs
   or use local-evaluation IDs against a linked production project.
2. Stop dispatch and scheduled work; wait for active native jobs and pipelines
   to terminate. Review an upgrade on a restored isolated database first. From
   the reviewed 105 baseline, apply missing append-only migrations in order:

   | Migration | Result |
   |---|---|
   | 106 | Universal MIT software features; server-owned hosted resource policy |
   | 107 | Pipeline checkpoints, immutable run identity and durable approvals |
   | 108 | Personal pipeline step queue, scoped device leases and profile limits |
   | 109 | Atomic demo activation and server-owned cleanup manifest |

3. Keep `deployment_policy.hosted=true` for CrewForm Cloud; only a database
   administrator chooses false for self-hosting. Removing licence gates must
   not remove quotas, native consent, encryption or workspace authorization.
4. Deploy matching task runner, frontend and the shared `cron-evaluate` Edge
   function. Preserve the function's configured gateway authentication mode:
   its handler verifies the configured internal secret. Keep one primary
   scheduler and preserve existing encryption/webhook secrets.
5. Verify workspace access, Cloud quota reservations, owner-only device grants,
   cancellation, a committed approval boundary and a deliberate invalid output
   contract. Use deterministic runtime peers for fault tests rather than real
   provider accounts. Run the local SQL/integration fixtures in disposable
   backends; do not run their transaction fixtures against customer data.

## CLI distribution

The CLI version is independent: **0.3.0**, with MIT licensing, `demo`, `doctor`
and `--device-profile`. Its tarball passed installation and an offline demo
smoke test. npm publication is pending local maintainer authentication; an
unversioned npm install may still resolve the original 0.2.0 package. Do not
assume the registry has changed because this platform release exists.

Until publication, build from a matching checkout:

```bash
npm --prefix cli ci
npm --prefix cli run build
node cli/dist/cli.js demo --output review-pack.json
node cli/dist/cli.js doctor --runtime codex:cli --json
```

The walkthrough makes no model calls and labels its outputs simulated. The real
supplied-patch review example needs installed agents, valid logins and human
review. Runtime diagnostics check executables, not authentication or eligibility.

## Recovery and device limits

- Continuation reuses committed step outputs only when input/configuration and
  execution authority still match. Human approval expires after 24 hours.
- Uncertain in-flight effects require review; there is no automatic replay,
  native session resume or approval for arbitrary external writes.
- Personal workers support single-agent tasks and sequential pipeline steps.
  Fan-out and other team modes cannot use paired devices. Up to six active
  owner-approved device profiles are allowed, with one native lease per owner
  and agent family across profiles, transports and workspaces.
- Provider logins stay local. Approved prompts/files reach the device and
  results/logs return to Cloud. No shared login pool or API fallback is added.
- Output contracts validate a bounded schema subset and data shape; they do
  not establish factual correctness. Native usage/cost remains unknown unless
  reported. Evidence exports are authorized and bounded, not unlimited archives.
- Demo cleanup lists tracked resources and their team run history, refuses
  edits or reuse, and requires active runs to be cancelled. Older demos can
  clear their marker without deleting any resources.

## Rollback and validation boundaries

Keep previous matching application images available. Stop dispatch before
rollback; retain additive tables and execution history instead of dropping
live records. A runtime older than 108 cannot coordinate personal pipeline
jobs; inspect and retire active jobs before restoring an older runner.
Database restoration is a separate controlled recovery operation. Operational
rollback does not revoke MIT rights already granted in published source.

Fresh-schema CI covers policy/quota enforcement, device leases, checkpoint
continuation, demo transactions, and deterministic CLI→ACP handoffs through the
actual personal-worker HTTP transport. It does not establish live payment
lifecycle coverage, provider subscription eligibility, general protocol
conformance, or ongoing automated backup coverage.
