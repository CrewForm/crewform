# Measuring first-run usefulness

Use consenting testers and concrete artifacts. No analytics beacon or automatic
upload is installed by this work. The offline demo and doctor JSON can be inspected
locally; users choose whether to share them.

For each trial, ask the tester to record:

| Measure | Definition |
|---|---|
| First artifact | A saved result the tester can inspect; record simulated and real execution separately |
| Time to first artifact | Time from starting the documented setup to opening the saved artifact |
| Setup failure | The blocking command, sanitized error, OS and CLI version; whether the next-action guidance resolved it |
| Repeat use | Whether the tester completes a second real workflow within seven days |
| Review usefulness | Whether findings cite supplied sources, what the critic rejected, and what the human still had to correct |

Use the optional first-run feedback issue form for users who choose to publish
technical feedback. Do not post prompts, repository content, native account details,
credentials or full logs without reviewing them. Private feedback can be summarized
as counts only with the participant's consent. Self-reported timings and fixture
results are not independent performance benchmarks.

Prioritize fixes from observed setup failures and incorrect outputs before adding
more protocols, templates or marketplace entries. A small cohort's reports identify
problems to investigate; they do not establish broad market demand.
